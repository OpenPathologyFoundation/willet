# WILLET UI Critical Review — Pathologist Perspective

**Date:** March 13, 2026
**Context:** Review of Stage 1 scaffold based on stream-of-consciousness feedback from the lead pathologist and examination of the running UI.

---

## 1. Distilled Insights from Pathologist Feedback

The feedback surfaced a fundamental tension in the current design that cuts across several specific complaints. Here is the core issue and its manifestations:

### 1.1 The Core Tension: Conversational vs. Direct Input

The SDS 04-03 architecture describes the prompt area as the pathologist's *primary* input mode — "conversational instruction." But in practice, pathologists frequently want to dictate directly into the report without any AI interpretation. The current design forces all voice input through the LLM pipeline, which creates friction in two scenarios:

**Scenario A — The experienced pathologist:** They know exactly what they want to say. "Adenocarcinoma, moderately differentiated. Margins uninvolved." They want this transcribed verbatim into the clause, not interpreted, not rearranged, not confidence-scored. The current architecture has no path for this.

**Scenario B — The correction loop:** The pathologist dictates something, the LLM interprets it slightly wrong, the pathologist corrects it, the LLM re-interprets the correction. Each round trip adds cognitive load. Direct dictation into a clause would have been faster.

The fix is not to abandon conversational authoring but to offer a **direct dictation mode** as a parallel input path. The two modes serve different cognitive states: conversational mode is for bulk population ("three polyps and an adenoma"), direct mode is for precision dictation into a specific clause.

### 1.2 Personal Preferences Are Missing

The system has no concept of a pathologist's personal preferences. Theme (light/dark) is stored in localStorage, but there is no user-scoped preferences model. The pathologist feedback specifically flagged:

- Default input mode (conversational vs. direct dictation)
- Default clause templates per specimen type
- Preferred part naming conventions
- Font size preferences
- Sidebar default state (expanded vs. collapsed)

These are not one-time settings — they shape how the pathologist interacts with WILLET on every case. Without a preferences system, every pathologist gets the same defaults, and the UI feels generic rather than personal.

### 1.3 Templates Are the Missing Accelerator

The pathologist described a workflow where they want a template pre-populated in the clause editor before they start authoring. For a colon resection, the template might pre-populate: DIAGNOSIS (empty), MARGIN (empty), ANCILLARY × 3 (LVI, PNI, lymph nodes — empty). The pathologist then fills in the blanks.

This is distinct from the LLM population model. Templates are deterministic, instant, and predictable. They represent institutional knowledge about what a complete report for a given specimen type should contain. The current system has no template mechanism — every report starts as a blank slate, and the pathologist either types each clause manually or relies on the LLM to infer structure.

### 1.4 Synoptic Reports Belong in the Layout, Not in a Clause

The current model handles synoptic data as a `SYNOPTIC_REF` clause type — a text reference like "See synoptic: CAP Colon 4.2.0.0." The pathologist feedback makes clear that synoptic reports need to be visible alongside the main report, not buried as a clause reference. They are populated from external data (tumor registry, CAP protocols) and may need to be reviewed, edited, and finalized independently.

This is a Phase 2 concern architecturally, but it has Phase 1 layout implications: the right side of the screen should be reserved for contextual panels (synoptic, clinical history, prior reports), not used exclusively for the clause editor.

### 1.5 The Sidebar is a Binary Switch, Not a Sliding Panel

The current sidebar snaps between 380px and 48px. The pathologist wants:

- A drag handle for continuous resizing
- Stepwise collapse: full → narrow (just the prompt input) → icon strip → hidden
- The sidebar to feel like a tool panel, not a fixed column

The 380px fixed width also wastes space on wide monitors and cramps the report on narrow ones.

## 2. Critical UI Examination

### 2.1 Layout: The Two-Column Split

**Current state:** The sidebar takes a fixed 380px. The main content area (`max-w-3xl` = 768px) is centered with `mx-auto`. On a 1920px display, this means roughly 380px sidebar + 768px content + ~772px of dead whitespace on the right.

**Problem:** The layout was designed for two panels but only uses one effectively. The right side of the main content area is empty space. This is where contextual information should go: clinical history expanded, prior reports, synoptic data, slide thumbnails.

**Recommendation:** Move to a three-zone layout:
```
┌──────────┬────────────────────────┬──────────┐
│ Prompt   │  Clause Editor         │ Context  │
│ Panel    │  (primary authoring)   │ Panel    │
│          │                        │          │
│ 280-400px│  flex-1                │ 280-400px│
│ resizable│                        │ optional │
└──────────┴────────────────────────┴──────────┘
```

The context panel (right) would house clinical history, synoptic data, slide inventory, and peripheral documents. It collapses to an icon strip when not needed. The clause editor fills the remaining space. This uses the full viewport productively.

### 2.2 Sidebar Interaction Model

**Current state:** Binary toggle — 380px or 48px. CSS `transition-[width] duration-200`. No drag handle.

**Problems:**
1. No intermediate states. A pathologist who just wants the prompt input visible (no history) has to keep the full 380px panel open.
2. No resize handle. The pathologist can't adjust the width to their preference.
3. The collapsed state (48px with vertical text) is dead space — it communicates nothing useful.

**Recommendation:** Implement a three-state sidebar with a drag handle:

| State | Width | Shows | Trigger |
|-------|-------|-------|---------|
| Full | 280–500px (draggable) | History + prompt input | Drag handle or expand button |
| Compact | ~160px | Prompt input only (no history) | Drag below threshold or click |
| Collapsed | 40px | Expand icon only | Drag to minimum or collapse button |

The drag handle should be a vertical strip on the right edge of the sidebar (standard panel resize pattern), not hidden.

### 2.3 The Clause Editor Experience

**Current state:** Each clause is a `<select>` badge + `<textarea>`, laid out horizontally with `gap-2`. The textarea auto-expands. Type badges are color-coded with 3-letter abbreviations (Dx, Mrg, Anc, Syn, Cmt).

**What works well:**
- The color-coded type badges are instantly scannable
- Auto-expanding textareas feel natural
- Keyboard navigation (Arrow Up/Down, Enter to add, Backspace to delete empty) is well-thought-out
- The "received as" annotation below the part header is a nice touch

**What needs improvement:**

1. **Font and spacing.** The clauses use `text-sm` (14px) with `py-0.5` (2px) vertical padding. Pathologists read diagnostic text all day. The text should be at least 15–16px (`text-base` or a custom size) with more breathing room between clauses (`py-1.5` or `py-2`). The current density makes the editor feel like a developer tool, not a clinical authoring surface.

2. **Type badge as `<select>`.** The `appearance-none` select is clever but deceptive — it looks like a static badge until you click it, and the dropdown menu is the browser's native select, which looks jarring against the custom UI. A custom dropdown (popover or menu) would feel more integrated and could show full type names with descriptions.

3. **No visual grouping.** Five clauses in a flat list don't communicate the report's structure. A subtle separator or grouping between DIAGNOSIS clauses and ANCILLARY clauses would help the pathologist see the report's shape at a glance.

4. **The "+ Add clause" button** is at the bottom, below all clauses. If the pathologist has 8 clauses and wants to add one after the 3rd, they have to click at the bottom and then rearrange. An insert-between option (hover to reveal an "add here" handle between clauses) would be more direct.

5. **No drag reordering.** Clauses can only be reordered via voice commands or undo/redo. A drag handle on each clause (left of the type badge) for manual reordering is expected in any list editor.

### 2.4 The Report Header

**Current state:** Case ID (monospace), specimen type (muted), status badge, patient demographics in a single line, clinical history below.

**What works:** Compact, informative, unobtrusive.

**What needs improvement:**

1. **Clinical history is truncated.** It's a single `text-xs` line. For complex cases, clinical history can be several paragraphs. It needs a "show more" expansion or should be moved to the context panel.

2. **No case navigation.** In the standalone harness, case selection is in the dev toolbar (outside the module). In production, Okapi handles navigation. But the header should at least show the case's position in the worklist (e.g., "3 of 12") to orient the pathologist.

### 2.5 The Prompt Area (Conversation Panel)

**Current state:** Chat-bubble UI with user messages right-aligned and system responses left-aligned. Empty state shows a prompt icon and example text. Input at bottom with mic button, text area, send button.

**What works:**
- The chat metaphor is familiar
- The empty state gives useful examples
- Voice recording visualization (pulsing dot + frequency bars) is nicely done

**What needs improvement:**

1. **The chat UI implies a conversation, but the interaction is command-driven.** The pathologist isn't chatting — they're issuing instructions. The bubbles, timestamps, and "3 actions applied" summaries add visual clutter to what should be a focused command interface. Consider: a simple scrolling log (monospaced, compact) instead of chat bubbles. Or a command palette metaphor.

2. **No indication of what the system did.** When the system applies actions, the response says "Populated Parts A, B, C with diagnoses" but doesn't show what was actually written. The pathologist has to look at the clause editor to verify. A diff-style summary ("Added to Part A: *Adenocarcinoma, moderately differentiated*") would close the feedback loop.

3. **The mic button is small and peripheral.** Voice is meant to be a primary input mode, but the mic button is a small icon to the left of the textarea, visually subordinate to the text input. If voice-first is the intent, the mic should be more prominent — perhaps a large toggle at the top of the prompt area, with the textarea appearing as a secondary option.

4. **No direct dictation target.** As noted in §1.1, there is no way to dictate directly into a clause. The mic button always routes through the LLM pipeline. A clause-level mic icon (or a global "dictate into focused field" mode) is needed.

### 2.6 The Finalize Flow

**Current state:** "Finalize Report" is a full-width blue button at the bottom of the scrollable content. Clicking it validates, generates HTML, opens the FinalizeDialog modal with InkEditor.

**Concern:** The Finalize button is always visible and prominent. For a case with incomplete clauses, it's a tempting target that will just show an error. Consider making it contextually dimmed (not just `disabled:opacity-50` during save) or moving it to the header area where it's accessible but not the visual terminus of the page.

### 2.7 Dark Theme and Clinical Readability

The light theme uses `#F9FAFB` background with `#111827` text — good contrast. The dark theme uses `#1E2124` background with `#F3F4F6` text — also good. Badge colors are appropriately adjusted for both themes.

**Concern:** The badge colors are pastel tints (10% opacity backgrounds). On the light theme, they're subtle enough to be missed. On the dark theme, they're more visible. Consider whether the badges should be slightly more saturated on light theme for better scannability.

## 4. Architectural Implications

### 4.1 Direct Dictation Mode

This requires a new voice input path that bypasses the LLM pipeline entirely:

```
Voice input → Whisper transcription → insert text at cursor position in focused clause
```

The PromptArea currently owns the mic button and voice pipeline. Direct dictation would need either:
- A per-clause mic icon (ClauseEditor owns its own recording state), or
- A global "dictation mode" toggle that redirects the existing mic to the focused clause

The global toggle is simpler and avoids duplicating the MediaRecorder/Whisper infrastructure. When dictation mode is active, the mic button in the PromptArea changes behavior: instead of submitting through the LLM, it transcribes and inserts directly into the last-focused clause editor.

### 4.2 Preferences Store

Preferences need to be stored server-side (via the auth-system user profile) so they follow the pathologist across devices and sessions. The scaffold API should include a `preferences` block, and a new endpoint should support updates:

```
GET  /api/user/preferences → { defaultMode, sidebarState, fontSize, theme, ... }
PUT  /api/user/preferences → update
```

In standalone mode, MSW mocks this and falls back to localStorage.

### 4.3 Templates

Templates are institutional data — they belong in the database, not in the client. A template is:

```typescript
interface ReportTemplate {
  id: string;
  specimenType: string;       // "Colon resection", "Prostate needle biopsy", etc.
  clauses: { type: ClauseType; placeholder: string }[];
  source: 'institutional' | 'personal';
}
```

The scaffold endpoint could include `suggestedTemplate` when a case has no authored diagnosis and a template matches the specimen type. Or the pathologist selects a template from a dropdown in the PartEditor header.

### 4.4 Three-Zone Layout

Moving from two-zone (sidebar + main) to three-zone (sidebar + main + context) is a significant layout change. It should be designed now even if the context panel is Phase 2 — the layout container should reserve the right zone and collapse it when no context content is available.

## 5. Prioritized Recommendations

### Immediate (Stage 1 polish, before Stage 2):

1. **Increase clause font size** to `text-base` (16px) and clause spacing to `py-1.5`
2. **Add drag handle to sidebar** for continuous resizing
3. **Add clause drag-reorder handles** (left of type badge)
4. **Add insert-between controls** (hover state between clauses)
5. **Make "Finalize" less visually dominant** when report is incomplete

### Stage 2:

6. **Direct dictation mode** with global toggle
7. **User preferences store** (server-backed, localStorage fallback)
8. **Specimen-type templates** (institutional + personal)
9. **Action diff summaries** in prompt history
10. **Three-zone layout** with collapsible context panel (right)

### Stage 3+:

11. **Synoptic report panel** in context zone
12. **Custom type dropdown** replacing native `<select>`
13. **Clause grouping/separators** by type category
14. **Clinical history expansion** in context panel
